# Deployment runbook: um790-backup (batch job)

Generated by genproj (docker-container capability, workload=batch,
registry=ghcr.io).

This image is a **batch job**, not a service: it runs to completion and exits.
It has no port, no health endpoint and no long-running process. Scheduling is
deliberately not generated here — run it from your scheduler (e.g. Dagu) or by
hand.

## 1. Build & publish the image

The repository's Buildkite pipeline (`.buildkite/pipeline.yml`) contains a
`docker_publish` step that builds the image for `linux/amd64` and
pushes it to `ghcr.io/nickbrett1/um790-backup` on every push to `main` (tagged with the commit
SHA and `latest`).

- Registry credentials are resolved at run time from Doppler
  (`common`/`prd`, secret `GHCR_UPDATE_TOKEN`) using the `DOPPLER_TOKEN` the
  agent's `environment` hook provides:
  - `GHCR_USERNAME` — the GHCR namespace the image is published under
  - the resolved `GHCR_UPDATE_TOKEN` — a **classic** PAT with the
    `write:packages` scope, used to push to GHCR

### One-time CI setup (agent `environment` hook)

Before the first push can publish an image, the agent must supply the registry
credentials:

1. In the agent's `environment` hook, export `DOPPLER_TOKEN` so the
   `docker_publish` step can read `GHCR_UPDATE_TOKEN` from Doppler
   (`common`/`prd`) at run time.
2. Confirm `plugins-path` is set in `buildkite-agent.cfg` — every step here
   uses a plugin, and agent v4 has no usable default.

The registry token never lands in the agent's `environment` hook, where
every job on the fleet could read it. See `.buildkite/README.md` for the full list of agent
prerequisites.

> GitHub **fine-grained** PATs cannot access the Container registry (GHCR)
> yet, and offer no "Packages: read & write" permission — do not use one here.

## 2. Run it

Always run with `--rm` and pin the commit SHA: an immutable image is the only
thing that makes a scheduled run reproducible.

```bash
docker run --rm \
  -v /srv:/srv:ro \
  -v /srv/.um790-backup:/srv/.um790-backup \
  -e RESTIC_PASSWORD \
  -e NTFY_URL \
  ghcr.io/nickbrett1/um790-backup:<commit-sha>
```

The mount set is a contract between this image and whoever invokes it. The
entrypoint must assert every path it expects exists and is readable, and exit
non-zero naming the missing path — a DAG/image mismatch then fails run #1 with
`/backup: not found` instead of silently producing an empty backup. Keep the
`-v` list in sync with the scheduler's definition.

## 3. Compose (ad-hoc runs)

`docker-compose.yml` is generated with `restart: "no"`, because a finished job
must not be restarted by Docker. `docker compose run --rm app` is equivalent to
the `docker run` above and reads the same `.env`.

## 4. Rolling back / pinning a version

Every image is tagged with its commit SHA as well as `latest`. Both the
scheduler and an ad-hoc run should pin the SHA:

1. Find the SHA of the last good commit (GHCR package page, or `git log`).
2. Use `ghcr.io/nickbrett1/um790-backup:<commit-sha>`.

There is **no Watchtower and no `latest` auto-update**, by design: a batch image
must never change between runs without a reviewed commit, and never mid-run.

## 5. Package visibility

The image is published to
`ghcr.io/nickbrett1/um790-backup`. The generated
Dockerfile carries
`org.opencontainers.image.source=https://github.com/nickbrett1/um790-backup`,
so GHCR links the package to this repo on first push: a **public repo yields a
public package** and the pulling host needs no credentials. A **private** repo
yields a private package — log the pulling host's Docker daemon in once with a
classic PAT that has the `read:packages` scope:

```bash
echo "$GHCR_READ_TOKEN" | docker login ghcr.io -u <github-user> --password-stdin
```

## 8. Networking

Network mode is `bridge`.

A batch job normally needs no network beyond the registry pull: keep
`networkMode: bridge` unless the job must reach a host-local service (e.g. a
database on the host), in which case `networkMode: host` is the supported
option.

Regenerate with `overwrite: true` to apply configuration changes to an existing
repo — existing app code is preserved; only generated infra files are updated.
