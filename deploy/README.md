# Deployment runbook: um790-backup (batch job)

Generated by genproj (docker-container capability, workload=batch,
registry=ghcr.io).

This image is a **batch job**, not a service: it runs to completion and exits.
It has no port, no health endpoint and no long-running process. Scheduling is
deliberately not generated here — run it from your scheduler (e.g. Dagu) or by
hand.

## 1. Build & publish the image

The repository's Buildkite pipeline (`.buildkite/pipeline.yml`) contains a
`docker_publish` step that builds the image for `linux/amd64` and
pushes it to `ghcr.io/nickbrett1/um790-backup` on every push to `main` (tagged with the commit
SHA and `latest`).

- Registry credentials are resolved at run time from Doppler
  (`common`/`prd`, secret `GHCR_UPDATE_TOKEN`) using the `DOPPLER_TOKEN` the
  agent's `environment` hook provides:
  - `GHCR_USERNAME` — the GHCR namespace the image is published under
  - the resolved `GHCR_UPDATE_TOKEN` — a **classic** PAT with the
    `write:packages` scope, used to push to GHCR

Publishing is gated, not automatic: `docker_publish` depends on the shell build,
the batch smoke gate **and** the offline retention gate (§2b). An image whose
retention decisions have not been exercised is not published at all.

Note the asymmetry, because it has bitten this pipeline: `docker_publish` running
green means the image **exists**. It does not mean the host will use it. Only the
`dagu_pin_bump` step (§4) makes it reachable, and a bump that fails after a
successful publish leaves a green image that nothing points at. On 2026-10-22
build 54 did exactly that — published the mailroom sqlite fix, then died on a
stale DAG path — so "the fix is deployed" and "the pipeline is red" were both
true at once.

### One-time CI setup (agent `environment` hook)

Before the first push can publish an image, the agent must supply the registry
credentials:

1. In the agent's `environment` hook, export `DOPPLER_TOKEN` so the
   `docker_publish` step can read `GHCR_UPDATE_TOKEN` from Doppler
   (`common`/`prd`) at run time.
2. Confirm `plugins-path` is set in `buildkite-agent.cfg` — every step here
   uses a plugin, and agent v4 has no usable default.

The registry token never lands in the agent's `environment` hook, where
every job on the fleet could read it. See `.buildkite/README.md` for the full list of agent
prerequisites.

> GitHub **fine-grained** PATs cannot access the Container registry (GHCR)
> yet, and offer no "Packages: read & write" permission — do not use one here.

### One-time CI setup (DAG pin bump)

The `dagu_pin_bump` step opens a PR against `nickbrett1/dagu-dags` pinning the
new SHA (§4). It needs one more secret, also in Doppler `common`/`prd`:

- `DAGU_DAGS_TOKEN` — a **fine-grained** PAT scoped to `nickbrett1/dagu-dags`
  with `Contents: read & write` and `Pull requests: read & write`.

Fine-grained is correct *here* (unlike GHCR above): this is a git push plus a
pull-request API call, not a package write, so it can be scoped to one
repository. The step resolves it from Doppler at run time, so it is never in the
agent's `environment` hook.

## 2. Gates that run before publish

**2a. Shell gate** — `shellcheck -x scripts/*.sh`, then the built image runs a
phase with `--dry-run` and must exit 0. This proves the image starts and that the
argv contract holds with no environment at all.

**2b. Retention gate** — `scripts/test-retention.sh`, run inside the built image
with `--network=none`. `--dry-run` cannot test retention: there is no NAS and no
repository history in CI for a policy to select from, and that selection is the
only part of `prune` that can lose data. So the gate drives the real code:

- `select_sweep_candidates` against synthetic `synosharesnapshot` names — a
  56-day window, the exact-cutoff boundary (56 kept, 57 deleted), unparseable
  names left alone, and the rule that the newest snapshot is never deleted even
  when every snapshot has expired;
- the real `RESTIC_KEEP_ARGS` applied to throwaway **local** repositories with
  backdated snapshots, asserting that ten same-day snapshots collapse to one and
  that the newest survives the policy.

It reads `RESTIC_KEEP_ARGS` from the runner rather than restating it, so changing
the policy without thinking about its effect fails the gate.

What this still does **not** cover: DSM. The real `synosharesnapshot list`
output, the actual snapshot name format, and the delete call have never run
against a NAS. Run the phases by hand once (§4) before enabling the schedule.

The same blind spot applies to `dumps`: the smoke gate returns before any phase
body runs, so the sqlite path has no CI coverage at all. Both of the last two
`dumps` defects (a quoted glob that made the `STATIC_SQLITE` exemption match
nothing, and the mailroom WAL/`CANTOPEN` fallback) lived in code no test
executes. Treat a hand-run against a database in the failing state as the test,
not a formality.

## 3. Run it

Always run with `--rm` and pin the commit SHA: an immutable image is the only
thing that makes a scheduled run reproducible.

```bash
doppler run --project um790-backup --config prd -- \
  docker run --rm \
    -v /srv:/srv:ro \
    -v /srv/.um790-backup:/srv/.um790-backup \
    -v /var/run/docker.sock:/var/run/docker.sock:ro \
    -v /srv/.um790-backup/ssh:/run/ssh:ro \
    -e RESTIC_PASSWORD \
    -e NTFY_URL \
    -e DAG_RUN_ID \
    -e MAX_SOURCE_GB \
    ghcr.io/nickbrett1/um790-backup:<commit-sha> <phase>
```

All four mounts are load-bearing, and each one is the difference between a phase
that works and a phase that fails or, worse, silently does less:

| Mount | Needed by | Without it |
|---|---|---|
| `/srv:ro` | every phase | `/srv is not mounted` at preflight |
| `/srv/.um790-backup` | every phase | state, staging and the installed exclude list are lost between phases |
| `/var/run/docker.sock:ro` | `config`, `dumps` | `docker daemon unreachable` at `config` — the run dies after preflight has taken the lock |
| `/srv/.um790-backup/ssh:ro` | all NAS work | restic and ssh cannot authenticate; every NAS phase fails |

`-e VAR` with no value forwards the variable from the invoking environment
rather than `-e VAR=value`, which keeps the password out of the process list.
Under `doppler run` the values come from Doppler, so they are never written to a
file on disk.

The mount set is a contract between this image and whoever invokes it. The
entrypoint must assert every path it expects exists and is readable, and exit
non-zero naming the missing path — a DAG/image mismatch then fails run #1 with
`/backup: not found` instead of silently producing an empty backup. Keep the
`-v` list in sync with the scheduler's definition.

### `/srv` is `ro`, and one phase has to write

`/srv:ro` is deliberate and stays. A backup must not perturb what it backs up,
and the phases only ever read from the source. The one apparent exception proves
the rule: `dumps` cannot open a WAL-mode database whose writers are short-lived,
because with no `-wal` present SQLite must create the `-shm` and `:ro` returns
`EROFS` (`SQLITE_CANTOPEN`, 14 — not `SQLITE_BUSY`, 5). The fix does not widen
the mount. It copies main **and** `-wal` into writable staging and dumps from the
copy, so the live file is never opened writable and never checkpointed. If you
are tempted to mount a data directory `rw` to make a dump work, that is the thing
this design declines.

### `MAX_SOURCE_GB`

The source-size guard, in whole gigabytes, measured on `/srv` **with the exclude
list applied**. It describes the backup set, not the disk: the raw `/srv` total
is roughly 19G larger than the payload (`/srv/appdata/backups`,
`/srv/appdata/marketdata` — the `/srv/backups` and `/srv/marketdata` trees until
the data move lands — the Postgres clusters, caches, Dagu's own state), and
counting that is why a correct source could fail this check.

It exists to catch a **wrong mount**, not normal growth — a `/srv` that suddenly
measures hundreds of gigabytes is a disk mounted in the wrong place. The default
(70 against ~45G of payload) is deliberately loose for that reason. Raise it when
the data genuinely grows; do not raise it to make a mount problem go away.

## 4. Promotion, pinning and rollback

Every image is tagged with its commit SHA as well as `latest`. **Only the SHA is
never used to run it.** *(sic — the SHA is the only tag used; `latest` is a
convenience for local experiments and must not appear in a scheduler.)*

Nobody edits the pin by hand any more. On a green `main` build, the
`dagu_pin_bump` step runs `scripts/bump-dagu-pin.sh`, which:

1. clones `nickbrett1/dagu-dags`,
2. rewrites the single `UM790_BACKUP_IMAGE:` line in
   `dags/ryzen/um790-backup.yaml`,
3. asserts that **exactly two lines changed** before pushing (a `sed` that ran
   away cannot reach the branch),
4. force-updates one branch, `auto/um790-backup-pin`, so successive builds
   refresh a single PR rather than leaving one branch per build, and
5. opens the PR — or reports the one that is already open.

The PR changes an image tag and nothing else. That DAG carries **no schedule key
at all**, so a merged bump cannot put a timer on the host; the ability to schedule
is a property of the definition, not permission granted by a filename. Adding the
schedule stays a separate, deliberate edit by a human, after the phases have been
run by hand.

**Do not treat a `.disabled` filename as a safety net.** This pipeline used that
suffix for a while and it was neither reviewable nor enforced. Dagu 2.21.0
discovers `*.yaml`/`*.yml` only, so `um790-backup.yaml.disabled` matched nothing
and never appeared in `dagu ls` — but it stayed reachable by absolute path, and on
2026-10-22 it was run five times by hand. Two things follow, and both are why the
suffix is gone:

- a file `dagu` can execute but cannot discover makes "what can run?" unanswerable
  from `dagu ls`;
- renaming it is not a disable. `dagu suspend um790-backup` is.

The pin is also live within about a minute of merging, with nobody pulling on the
host: `dagu-dags-autocommit` fetches, rebases and pushes every minute, which means
it pulls too. There is no window in which a human notices a bad pin before it
runs. That is why the script refuses to move the pin backwards (a retried or
out-of-order build is normal here — build 40 was itself a retry), and why the
guard asks the GitHub compare API rather than local git.

Rollback, in order of preference:

1. Revert the pin commit (or set the SHA back) — one line, takes effect on the
   next invocation.
2. If the bad image already ran `prune`, the undo is the NAS snapshot from
   before it, not a re-deploy. `SNAPSHOT_RETENTION_WEEKS` is the window.

There is **no Watchtower and no tag auto-update**, by design, and the reason is
specific to this pipeline rather than general conservatism:

- each phase is a separate `docker run --rm`, so an image that changes between
  phases — or between a failed `prune` and its retry — makes the failure
  unreproducible and the retry not identical;
- `prune` can destroy snapshot history, and a bad pin costs a one-line revert
  while a bad channel is already published by the time you notice.

Watchtower would not even work here: it resolves tags and recreates running
containers, and this is a digest-pinned batch job with no container to recreate.
"Auto-pull" for this job is really just "drop the pin", which is the thing being
declined.

## 5. Package visibility

The image is published to
`ghcr.io/nickbrett1/um790-backup`. The generated
Dockerfile carries
`org.opencontainers.image.source=https://github.com/nickbrett1/um790-backup`,
so GHCR links the package to this repo on first push: a **public repo yields a
public package** and the pulling host needs no credentials. A **private repo**
yields a private package — log the pulling host's Docker daemon in once with a
classic PAT that has the `read:packages` scope:

```bash
echo "$GHCR_READ_TOKEN" | docker login ghcr.io -u <github-user> --password-stdin
```

## 6. Data mounts

`dataMounts` in the genproj config produces the `-v` flags in the run command
above and the `volumes:` block in `docker-compose.yml`. Mounts are read-only
unless the entry sets `"readOnly": false`.

The generated config produces only the first two (§3 table); the docker socket
and the ssh directory are hand-added, because they are this project's specific
requirements rather than generic batch-job mounts. Treat all four as the contract
and copy them from `docker-compose.yml` rather than from memory.

## 7. Environment variables

Keys are derived from the `envVars` configuration; nothing is invented here.

```bash
RESTIC_PASSWORD=
NTFY_URL=
```

Plus the NAS block (`RESTIC_REPOSITORY`, `NAS_HOST`, `NAS_PORT`, `NAS_USER`),
the per-run `DAG_RUN_ID`, and `MAX_SOURCE_GB` — all documented with real
defaults in `.env.example`.

Retention knobs are read by the runner and default to the documented contract;
set them only to deviate from it. `SNAPSHOT_RETENTION_WEEKS` (default 8) is the
NAS-side undo window and is deliberately independent of the schedule cadence, so
a cron change cannot silently shrink it.

## 8. Networking

Network mode is `bridge`.

A batch job normally needs no network beyond the registry pull: keep
`networkMode: bridge` unless the job must reach a host-local service (e.g. a
database on the host), in which case `networkMode: host` is the supported
option.

Regenerate with `overwrite: true` to apply configuration changes to an existing
repo — existing app code is preserved; only generated infra files are updated.
