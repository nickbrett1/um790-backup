# Exclude list for `restic backup /srv`. One pattern per line; blank lines and
# #-comments are ignored by restic. Installed to /srv/.um790-backup/exclude.txt
# by the preflight phase, so edit this file - not the copy on the host, which is
# overwritten from the image on every run.
#
# DO NOT EXCLUDE $BASE (/srv/.um790-backup) AS A WHOLE.
#
# This list used to carry exactly that line, justified as "staging is not listed
# separately: it lives at /srv/.um790-backup/staging and the directory below
# covers it". That reasoning was backwards, and it silently destroyed the
# backup. do_backup runs
#
#     restic backup /srv "$STAGE"
#
# i.e. staging is an EXPLICIT SECOND TARGET, and restic drops an explicitly
# named path that falls beneath an excluded ancestor. The config/, pg/ and
# sqlite/ subtrees the two preceding phases had just produced were discarded at
# snapshot time - while every guard reported success, because do_backup's
# completeness check reads staging on DISK and never the resulting snapshot.
#
# Measured against both pre-existing snapshots: 0 paths under staging, 0
# *.dump, 0 containers.txt; only the bare parent directory was recorded. The
# Postgres dumps are the ONLY coverage those four clusters have - their raw
# data directories are excluded below on the grounds that pg_dump covers them -
# so the databases had no backup by either route.
#
# The fix is to exclude staging's SIBLINGS instead of its parent, so the /srv
# walk still skips runtime state while the explicit staging target survives.
# Each entry here lives directly under $BASE:
#
#   state/         run.lock, *.epoch, last_success.json - runtime bookkeeping
#   cache/         restic's local cache - rebuildable, and it churns per run
#   ssh/           restic/NAS private keys - secrets, must never be snapshotted
#   staging/.tmp/  dump scratch space; empty on success, but a failed run can
#                  leave a multi-GB partial behind
#
# staging/config, staging/pg and staging/sqlite are deliberately NOT excluded:
# they are the payload. Verified with this image's restic 0.18.1 - an explicit
# target below an excluded parent contributed 0 files, the same inputs with
# sibling-only excludes contributed 1.
/srv/.um790-backup/state
/srv/.um790-backup/cache
/srv/.um790-backup/ssh
/srv/.um790-backup/staging/.tmp

# /srv/backups — this host's OWN backup output, deliberately PART-covered.
#
# The blanket `/srv/backups` line that used to live here was justified as
# "other machines' data: large, and not ours to restore". That was wrong on the
# facts. The directory has exactly three children and every one of them is this
# host's own service data. Verified 2026-10-22: no bind mounts, no nested
# mounts, no symlink escaping the tree (the one symlink is
# obsidian-vault/latest.tar.gz -> a file in the same directory, relative).
#
#   potato/          1.6M   potato-backup DAG output: project.sqlite + state tar
#   obsidian-vault/  20M    obsidian-vault-backup DAG output: nightly tarball
#   msgvault/        5.8G   msgvault-native repo, 73 snapshots to 2026-08-16
#
# The first two are now INCLUDED. They are small, clean (no special files, no
# hardlinks, not sparse) and append-only at one file per day, so restic dedup
# stores roughly 2.6M/night. Excluding them meant those two DAGs were writing
# backups onto the same NVMe partition they exist to protect: /srv/backups and
# /srv are one ext4 filesystem on /dev/nvme0n1p2 (same st_dev 66306), and
# nothing on this host moves the directory off it - no rsync/rclone/scp/
# syncthing/btrfs-send in the DAG repo or /srv/stack, empty user crontab, stock
# /etc/cron.d, all stock systemd timers, no NFS/SMB export.
#
# msgvault/ by contrast stays EXCLUDED, and is slated for deletion once the
# msgvault-backup DAG is disabled:
#   - its subject, /srv/msgvault/msgvault.db, is dumped by the dumps phase AND
#     copied raw by the /srv walk, so this repo is a third copy of the same data;
#   - nothing prunes it. 73 .mvmanifest snapshots back to repo creation
#     (2026-08-16), growing without bound, 5.8G today;
#   - config.toml says encryption = "none", so it is an unencrypted plaintext
#     second copy of the entire mail archive sitting on a share.
# ORDER MATTERS on removal: disable the DAG BEFORE deleting the directory, or
# its next 04:00 tick recreates it. compose mounts /srv/backups/msgvault:/backup
# and the DAG runs `msgvault backup create --repo /backup`.
#
# WHY THE CHILDREN ARE NAMED RATHER THAN THE PARENT PLUS A NEGATION: restic
# 0.18.1 has no negation syntax at all. A `!/srv/backups/something` line is
# treated as a literal path pattern starting with '!', matches nothing, and
# produces no warning and no error - verified empirically against the pinned
# binary, not inferred from docs. The only way to include a subdirectory of an
# excluded parent is to narrow or drop the parent exclusion, which is what this
# block does. (The `restic help backup` exclude surface offers only
# --exclude, --iexclude, their -file forms, --exclude-if-present,
# --exclude-caches and --exclude-larger-than.)
/srv/backups/msgvault

# TRANSITIONAL: the /srv/data mirror lines, added BEFORE the host move.
#
# The service data trees are being relocated from /srv/<name> to /srv/data/<name>
# (reader, msgvault, marketdata, data-scout, backups). The /srv/data lines below
# are added while the /srv/<name> originals they mirror are STILL PRESENT, and
# the originals are to be deleted in a FOLLOW-UP commit once the move is
# verified on the host.
#
# Both sets must be here in the meantime, on purpose. The image is pinned before
# the data actually moves, so for a while either path may be the live one. A
# window in which neither the old nor the new path is excluded does not fail
# loudly: the nightly run just backs up ~15G it exists to skip, silently and
# expensively. Keeping both costs three dead pattern lines that match nothing.
#
# TO REMOVE after the move: the /srv/<name> originals (/srv/backups/msgvault,
# /srv/marketdata, /srv/msgvault/backup-cache) and this comment block. NOT the
# /srv/datasets* lines further down - that store is not moving.
/srv/data/backups/msgvault

# Other machines' data: large, and not ours to restore.
/srv/marketdata
# transitional /srv/data mirror - see the block above.
/srv/data/marketdata

# The data-scout dataset store: a SECOND FILESYSTEM mounted over this tree.
#
# /srv/datasets (the @datasets subvolume) and /srv/datasets-cache (@cache) are
# one btrfs filesystem on a second NVMe - UUID
# 21d8744e-1425-4d9e-94ea-3361b9139a9c - mounted over /srv's ext4 tree. restic
# walks into mounts (this job passes no --one-file-system, and that default is
# load-bearing: it is also why bind-mounted service data is visible), so without
# the two lines below a single nightly run copies the entire store to the NAS.
#
#   /srv/datasets-cache   pure reflink-shared object storage: every byte in it
#                         is a reflink of something under a dataset's data/, so
#                         a snapshot of the cache alone restores nothing that
#                         could not be rebuilt from the payload. Never worth a
#                         byte.
#   /srv/datasets/*/data  the payload half of each dataset - the large,
#                         re-obtainable part.
#
# The REST of each dataset directory is deliberately NOT excluded: README,
# dvc.yaml, findings and the per-dataset git repository. They are small and
# cannot be regenerated from anywhere, so they are the part a restore needs.
#
# `*` does not cross a '/' (restic matches per path component), so the glob
# covers exactly one level: the data/ of a dataset sitting directly under
# /srv/datasets. It matches NOTHING today - no dataset has been imported yet -
# which is why it is safe to land before the first import.
#
# A dataset whose README says `reproducible: no` is the only copy of itself, so
# its data must stay in the backup. NOTE that removing "its exclusion" is not
# something this file can express while the glob above stands: a line cannot
# carve one dataset back out of a pattern that matches it (restic 0.18.1 has no
# negation - see the msgvault block above). Carving one out means narrowing the
# glob to the reproducible datasets by name. Whoever imports such a dataset owns
# that edit; do not assume the glob has it covered.
/srv/datasets-cache
/srv/datasets/*/data
