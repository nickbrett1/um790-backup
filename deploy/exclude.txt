# Exclude list for `restic backup /srv`. One pattern per line; blank lines and
# #-comments are ignored by restic. Installed to /srv/.um790-backup/exclude.txt
# by the preflight phase, so edit this file - not the copy on the host, which is
# overwritten from the image on every run.
#
# DO NOT EXCLUDE $BASE (/srv/.um790-backup) AS A WHOLE.
#
# This list used to carry exactly that line, justified as "staging is not listed
# separately: it lives at /srv/.um790-backup/staging and the directory below
# covers it". That reasoning was backwards, and it silently destroyed the
# backup. do_backup runs
#
#     restic backup /srv "$STAGE"
#
# i.e. staging is an EXPLICIT SECOND TARGET, and restic drops an explicitly
# named path that falls beneath an excluded ancestor. The config/, pg/ and
# sqlite/ subtrees the two preceding phases had just produced were discarded at
# snapshot time - while every guard reported success, because do_backup's
# completeness check reads staging on DISK and never the resulting snapshot.
#
# Measured against both pre-existing snapshots: 0 paths under staging, 0
# *.dump, 0 containers.txt; only the bare parent directory was recorded. The
# Postgres dumps are the ONLY coverage those four clusters have - their raw
# data directories are excluded below on the grounds that pg_dump covers them -
# so the databases had no backup by either route.
#
# The fix is to exclude staging's SIBLINGS instead of its parent, so the /srv
# walk still skips runtime state while the explicit staging target survives.
# Each entry here lives directly under $BASE:
#
#   state/         run.lock, *.epoch, last_success.json - runtime bookkeeping
#   cache/         restic's local cache - rebuildable, and it churns per run
#   ssh/           restic/NAS private keys - secrets, must never be snapshotted
#   staging/.tmp/  dump scratch space; empty on success, but a failed run can
#                  leave a multi-GB partial behind
#
# staging/config, staging/pg and staging/sqlite are deliberately NOT excluded:
# they are the payload. Verified with this image's restic 0.18.1 - an explicit
# target below an excluded parent contributed 0 files, the same inputs with
# sibling-only excludes contributed 1.
/srv/.um790-backup/state
/srv/.um790-backup/cache
/srv/.um790-backup/ssh
/srv/.um790-backup/staging/.tmp

# /srv/appdata/backups — this host's OWN backup output, deliberately PART-covered.
#
# The blanket `/srv/backups` line that used to live here was justified as
# "other machines' data: large, and not ours to restore". That was wrong on the
# facts: every child of that directory was this host's own service data.
# Verified 2026-10-22: no bind mounts, no nested mounts, no symlink escaping the
# tree (the one symlink is obsidian-vault/latest.tar.gz -> a file in the same
# directory, relative).
#
# The tree MOVED to /srv/appdata/backups on 2026-10-30 (reader, msgvault,
# marketdata, data-scout, backups -> /srv/appdata/<name>), so the patterns here
# name the new parent. As of that move it holds:
#
#   obsidian-vault/  41M   obsidian-vault-backup DAG output, nightly 04:30
#   um790-backup-manual-20261023T1045Z/  32K  stale run logs, awaiting deletion
#
# obsidian-vault/ is INCLUDED. It is small, clean (no special files, no
# hardlinks, not sparse) and append-only at one file per day, so restic dedup
# stores roughly 2.6M/night. Excluding it meant that DAG wrote its backups onto
# the same NVMe partition they exist to protect.
#
# TWO CHILDREN ARE GONE, and their exclude lines went with them - a pattern that
# matches nothing protects nothing:
#
#   potato/     deleted 2026-10-30 (1.6M of potato-backup DAG output)
#   msgvault/   deleted 2026-10-30 (5.8G native repo, 73 snapshots from
#               2026-08-16, frozen since 2026-10-22). It was not the only copy:
#               /srv/appdata/msgvault/msgvault.db is dumped by the dumps phase
#               AND copied raw by the /srv walk, so this repo was a third copy -
#               unencrypted (encryption = "none") and pruned by nothing. Its own
#               mount was removed from compose at the same time.
#
# WHY THE CHILDREN ARE NAMED RATHER THAN THE PARENT PLUS A NEGATION: restic
# 0.18.1 has no negation syntax at all. A `!/srv/appdata/backups/something` line
# is treated as a literal path pattern starting with '!', matches nothing, and
# produces no warning and no error - verified empirically against the pinned
# binary, not inferred from docs. The only way to include a subdirectory of an
# excluded parent is to narrow or drop the parent exclusion, which is what this
# block does. (The `restic help backup` exclude surface offers only
# --exclude, --iexclude, their -file forms, --exclude-if-present,
# --exclude-caches and --exclude-larger-than.)
#
# NOTE: nothing here is excluded under /srv/appdata/backups today. The block is
# kept because it is the written record of why the parent is not excluded, and
# because the next backup output to land there will need the same reasoning.

# MIGRATION COMPLETE 2026-10-30 — the /srv -> /srv/appdata transitional belt is
# REMOVED, and this is the commit that removes it.
#
# The previous revision carried both sets of patterns on purpose: the image is
# built and pinned BEFORE the host move, so for a window either path could be the
# live one, and a window in which neither is excluded does not fail loudly - the
# nightly run just backs up ~15G it exists to skip, silently and expensively. The
# /srv/<name> originals and the appdata mirrors of them have now been verified
# absent on the host, so they are gone from this file:
#
#   /srv/backups/msgvault         gone (store deleted; see the block above)
#   /srv/marketdata               gone (dissolved - see below)
#   /srv/appdata/marketdata       gone (dissolved - see below)
#   /srv/msgvault/backup-cache    gone (tree is now /srv/appdata/msgvault)
#
# An exclude that matches nothing is inert HERE but must never be added to
# SQLITE_DBS, where an entry naming an absent path is a HARD FAILURE - that is
# why the transition belt belonged in this file and not in that array.

# /srv/appdata/marketdata NO LONGER EXISTS, and its two halves went to two
# different places on 2026-10-30. The name was a NAS-era container name; the move
# finally showed it was holding two unlike things:
#
#   13G Databento payload  -> /srv/datasets/databento  (a DATASET: DVC, btrfs
#                             store, backed up by default - see below)
#   264K request book      -> /srv/appdata/data-sourcing-agent/requests
#                             (an AGENT's state: git-tracked, pushed to
#                             github.com/nickbrett1/marketdata-requests)
#
# Neither is excluded, and both are now in the backup. Do not recreate
# /srv/appdata/marketdata as an umbrella for either one; the split is the point.
#
# /srv/appdata/data-sourcing-agent/state is new on the same day (the agent's own
# bookkeeping) and is protected by the same absence. Neither requests/ nor state/
# may ever acquire a line here: requests/ is the only record of what was ordered,
# so an exclusion covering the agent's directory would take it along silently.

# The data-scout dataset store: a SECOND FILESYSTEM mounted over this tree.
#
# /srv/datasets (the @datasets subvolume) and /srv/datasets-cache (@cache) are
# one btrfs filesystem on a second NVMe - UUID
# 21d8744e-1425-4d9e-94ea-3361b9139a9c - mounted over /srv's ext4 tree. restic
# walks into mounts (this job passes no --one-file-system, and that default is
# load-bearing: it is also why bind-mounted service data is visible), so the
# store falls into the snapshot by the ordinary /srv walk, and only a line in
# this file can take a part of it back out.
#
# DATASET PAYLOADS ARE BACKED UP BY DEFAULT. For a backup system the default has
# to be "protected": an absent line here means the data is in the snapshot.
# Each dataset's data/ is therefore included with no entry in this file at all.
#
# This block used to carry `/srv/datasets/*/data`, justified as "the payload
# half - the large, re-obtainable part". That inverted the default in the worst
# possible direction: it left the most valuable data on the host UNPROTECTED
# unless someone noticed the glob and acted on it, and a glob cannot be
# un-applied to one dataset (restic 0.18.1 has no negation - see the msgvault
# history above), so "carving one dataset back out" was not expressible here
# either. Policy inverted on 2026-10-30: payloads in, exclusion explicit.
#
# EXCLUSION IS NOW EXPLICIT AND PER-DATASET. A dataset may be excluded only by
# naming its exact path in this file, with the reason on the same line, and only
# when its own README declares `reproducible: yes` - i.e. its payload can be
# regenerated from upstream:
#
#   /srv/datasets/<name>/data   # reproducible: yes, rebuilt by `dvc repro`
#
# A dataset whose README says `reproducible: no`, or says nothing, is the only
# copy of itself; its data/ must stay in the backup. Do not reintroduce a glob
# or a wildcard here: the whole point of naming one path is that every other
# dataset - and every dataset imported later - inherits protection without an
# edit.
#
# THE FIRST REAL DATASET IS NOW THERE: /srv/datasets/databento, 13G - 10 XNAS +
# 1 MEMX MBO batches, raw plus 7 converted Parquet batches, imported 2026-10-30
# from the old /srv/appdata/marketdata/backup tree and verified byte-exact
# before the source was deleted. It has NO LINE HERE and is therefore protected
# in full, its DVC-managed data/ included. Two structural facts about it matter
# to a future exclude:
#
#   - its payload lives under data/, and Databento's condition.json,
#     manifest.json and metadata.json were lifted OUT of the batch directories
#     into a sibling receipt/ tree precisely so that an exclude matching data/
#     cannot lose the provenance of the payload it removes;
#   - data/parquet/*.parquet are relative SYMLINKS into the batch directories
#     (a flat index for tools that glob one directory), not extra copies.
#
# The REST of each dataset directory - README, dvc.yaml, findings and the
# per-dataset git repository - was never excluded: small, and not regenerable
# from anywhere. Together with data/ they are what a restore needs.
#
# /srv/datasets-cache STAYS EXCLUDED, and that is a technical fact rather than
# policy: it is pure reflink-shared object storage, so every byte in it is a
# reflink of something under a dataset's data/, which is now itself in the
# backup. A snapshot of the cache adds bytes and no recoverable information -
# the payload beside it already holds every one of them.
#
# It is also EMPTY today (verified 2026-10-30: du reports 0 and find counts no
# entries below it, the databento import having moved the payload into the
# dataset), so this line currently removes nothing from the backup. It is kept
# rather than deleted because the cache is where the NEXT import's objects land,
# and a line that has to be re-added under time pressure during an import is a
# line that gets forgotten. "Matches nothing today" is not a reason to drop it
# here - unlike the transitional patterns retired above, which named paths that
# no longer exist and will not come back.
/srv/datasets-cache
